## Implemented local production paths

`native_candidates.py build` requires a clean native-host checkout, completed policy, reviewed same-commit evidence and local companion recipe. It freezes the backend, compiles TypeScript, packages only that target in a temporary extension (without the legacy Python prepublish hook), probes the extracted VSIX and assembles/validates the full offline companion. The companion backend executable must match the built executable. Relative recipe input paths resolve from the recipe directory. Model/runtime files must already exist; no asset download is performed by this tool. `aggregate` accepts exactly six matching candidate records and checks their complete transport inventory, removing a failed inventory rather than retaining an apparently approved record.

The inactive six-runner builder consumes owner-reviewed target input artifacts and uploads `thread-release-inventory` only after aggregation. The required recipe/evidence artifacts and real platform checks still need to be prepared and executed. Their evidence is reviewed input, not inferred from successful build fixtures. A locally generated backend may differ from an earlier recipe; mismatching bytes deliberately stop the build and require a freshly reviewed recipe.

`marketplace_upload.py` defaults to read-only planning. Execution additionally requires the enabled exact-commit main job; it uses already authenticated `vsce --azure-credential`. An exclusive ledger lock prevents concurrent execution. It records `uploading` before each call, then `uploaded` and finally `verified` after the public Marketplace query confirms exact publisher/name/version/target/preview channel. Uploaded targets resume listing verification without re-uploading; uncertain outcomes require owner reconciliation. A different commit/version/package hash cannot reuse the ledger. Existing Marketplace versions without matching ledger provenance stop instead of being treated as newly approved bytes. Listing verification establishes visibility/channel, not installability or equality of Marketplace-transformed package bytes; real clean-machine install checks remain required.

The inactive publishing workflow saves the recovery ledger even on failure and accepts an explicit prior run/attempt for ledger restoration. It never automatically retries an uncertain upload. Missing prior ledgers cannot silently adopt existing listings. Keep ledger artifacts for recovery; a crash may leave a `.lock` or `.tmp` requiring inspection and owner reconciliation before retry. All Actions in both inactive drafts are now pinned to official upstream commits recorded in `release/action-pins.json`. The five actions/* commits have verified signatures; Azure Login v3 tag provenance is verified but GitHub reports its commit signature unverified. Re-review pins for security updates before activation. No pipeline was activated or executed in this local preparation.
